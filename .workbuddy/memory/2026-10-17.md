# 2026-10-17

## v7 Python → C#/.NET 10 迁移：从"无法编译的骨架"重写为可用实现

交付的 Gemini 生成代码只是一个约 1000 行的残缺骨架，无法编译。它缺：
ffprobe 探测、编码器能力探测、滤镜/缩放算法探测、编码前预检、时间码解析、
音频通路、CLI 参数、尺寸归一化。FrameRingBuffer 还有 use-after-return bug
（ArrayPool 归还后控制器仍持有 previous 帧引用）。

### 做法
按 live_archive_encoder.py v6.3.3（2640 行）完整重写 C# 项目，严格对齐语义，
再在安全处做性能优化。

关键对齐点（容易出错，下次注意）：
- Python 的 `time.sleep` 时基在超时时**重置**(`next_deadline = perf_counter()`)，
  不追赶。C# 也必须重置，不能用整数 tick 累加，否则行为不同。
- 状态机有 `elif target < current_level and rate < limit*1.10: 0.80s 后降级`
  分支，容易被漏掉。
- `f"{fps:g}"` 是 6 位有效数字，C# 要用 `"G6"`，不能用默认 "G"（往返格式）。
- Python `deque(maxlen=N)` + `captured[-1]; captured.clear()` → 取最新丢弃其余。
- 高分辨率定时器的**自旋收尾很危险**：每 slot 自旋 1ms 让 C# CPU 从 0.19s
  飙到 1.41s（Python 是 0.19s）。改成 sleep 到绝对 deadline 后降到 0.65s。

### 性能结论（重要，别再重复期待）
实时节奏是刻意设计（capture 线程和主循环都按墙钟等待），所以**迁移不会让
编码变快**。实测 20s 素材：Python 21.65s / C# 21.35s，只快 1%。
控制器 CPU 是固定启动开销（5s 素材 0.656s，20s 素材 0.48-0.77s，不随 slot 增长），
比 Python 高约 0.45s，来源是 JIT。内存 61MB vs 15MB 是 .NET 运行时地板。

### 环境限制
- NuGet 走代理 127.0.0.1:1418 返回 502，**ReadyToRun / NativeAOT 都装不上**。
  只能用离线开关：InvariantGlobalization / UseSystemResourceKeys /
  MetadataUpdaterSupport=false / System.GC.Conserve=7（实测无明显收益）。
- 测速素材用 lavfi 生成 20s 320x240 h264+aac 放 tests/media/test_src.mp4。

### 验证结果
- 12/12 编码器矩阵 PASS（rv20/mpeg4/libx264/mpeg1video/wmv2/mjpeg/roq/h261/
  时间范围/无裁剪/反交错/低帧率），9/12 的 fresh/repeated 逐帧完全一致。
- 关掉节流（--limit 99999）时两边 fresh=64 repeated=1 **完全一致**，
  证明帧管线等价；剩余差异是自适应状态机对实时抖动的响应
  （Python 自己跑三次也是 37/67/64）。
- 11/11 错误路径退出码和消息一致。
- 真实素材 60s：780 slots 完全一致，码率差 0.13%，文件大小差 0.09%。

## 第二轮：AOT / SIMD / 分离音频（用户要求）

### AOT（已打通）
- 之前失败原因：`link.exe` 找不到 `advapi32.lib`。ILCompiler 的
  `findvcvarsall.bat` 会调 `vcvarsall.bat` 取 `%LIB%`，而 vcvarsall 的
  Windows SDK 探测走 **reg.exe**，在构建沙箱里被拦截，所以 LIB 只含 MSVC 两个
  目录、没有 `Windows Kits\10\Lib\<ver>\um\x64` 和 `ucrt\x64`。
- 解法：用官方扩展点 `AdditionalNativeLibraryDirectories` 显式补这两个目录
  （csproj 里的 `WindowsSdkLibRoot` / `WindowsSdkLibVersion`，可命令行覆盖）。
  正常开发机上可以删掉这段。
- 结果：3.76 MB 单文件 exe；冷启动 168ms → 116ms（`--cpu-info`，7 次取 min）。
- **重要坑**：NativeAOT 默认按 **SSE2 基线**编译，所以
  `Vector<byte>.Count=16`、`Avx2.IsSupported=False`（JIT 是 32 / True）。
  要提升基线用 `-p:IlcInstructionSet=avx2`，代价是 exe 变得挑 CPU。

### SIMD：没有可开的东西
- FFmpeg 侧已经运行时派发，实测 `-cpuflags 0`（关 SIMD）比默认慢 1.2–1.5x；
  强制 `+avx2` 与默认无差别，`+avx512` 反而略慢；libx264 在这段小样本上
  完全不敏感。
- C# 侧没有可向量化的活：控制器只是把解码器 stdout 的帧搬到编码器 stdin，
  从不碰像素。

### 分离音频（split）：做了，但**不能当默认**，也不快
- 结论（5s 片段、每变体 4 次，ab_duration.py）：
  - inline：duration 与 py 完全一致且**确定性**；fresh/repeat 落在 py 的抖动带内。
  - separate：mpeg1video 的 fresh 从 56 掉到 32，duration 在 4.901/4.984 之间
    跳；wmv2 帧完全相同（33/32）但 duration 从 5.046 变 5.015（`-c copy`
    重封装改写了 ASF 的 duration 字段）。
  - separate 比 inline **慢约 0.7s**（视频段被墙钟钉死，音频+重封装是纯增量）。
- 因此默认改回 `inline`（= v6.3.3），`separate`/`auto` 保留为可选项。
  音频进程降到 `BelowNormal` 优先级并不能消除扰动。
- split 的安全网值得保留：RoQ muxer 会 rc=0 但静默丢视频流；
  rv20/RealMedia 会产出 HEADER ERROR 的文件。靠 `CanSplitMux`（3 帧预演）
  + `VerifyMuxedOutput`（重新 probe + `ffmpeg -f null -` 解码校验）拦住。

## Bug fix：CUI 里中断一次后，后续编码全部秒退 "Interrupted."
- **根因**：`Program` 只有 `private static readonly CancellationTokenSource
  InterruptSource`。Ctrl+C 处理器取消它之后**从不重置**，而 CUI 中断后不退出，
  于是同会话里后续所有编码都拿到已取消的令牌，在 Execute 循环首行
  `ThrowIfCancellationRequested()` 就抛出。特征：打印完 `Filters :` 立刻中断，
  一秒活没干。
- 排查确认取消**只有这一个来源**：`Execute()` 里那个 linked CTS 只用于停
  diagnostics 读线程，不会反向取消父令牌（linked 是单向的）。
- **修法**：新增 `src/LiveArchiveEncoder/Core/Interrupt.cs` 统一收口，
  关键是把令牌改成**按操作发放**——`BeginOperation()` 返回前先清掉上一次的
  取消状态。CUI 每次 Start encoding 和 CLI 每次运行各调一次。
  `Cui.Run` 不再接收 token 参数，改为在 `StartEncoding` 内部取。
- **验证方式（可复用）**：把真实 `Interrupt.cs` 用 `<Compile Include>` 编进一个
  临时控制台工程，直接调 `Request()` 模拟 Ctrl+C，断言
  `BeginOperation()` 返回的下一个令牌 `IsCancellationRequested == false`。
  比想办法真的发 Ctrl+C 事件可靠得多。
- 另用 stdin 驱动真实 CUI 跑了一次「编码 → 编码」，两次都完成。
- 回归：矩阵 12/12、错误路径 11/11，AOT 产物冒烟通过。

## 分段并行编码猜想 —— 验证 + 实现（用户提议，实测否掉了一半）

用户猜想：把 00:00-05:00 切成 10 段并行编码，速度会不会增长？
先验证再动手，结论：**猜想成立但找错了瓶颈**。报告落在
`tests/PARALLEL_SPLIT_VERIFICATION.md`。

### 关键实测数据（320x240 h264 / 20s 源）
- 1 路 10s 编码墙钟 11.54s；**4 路并行 12.15s**，CPU 只 0.45s→0.96s。**96% 墙钟在 sleep。**
- 20s 素材真实计算量 ≈0.28s CPU，占墙钟 **1.4%**。
- 去掉节流的直通管道：**0.345s**（58×），260 帧、duration 20.000 全对。
- 主循环 `slotInterval=1/fps` + `WaitUntil`（RealtimeEncoder 552/598-601），
  **采集线程 530-533 也有一处墙钟节流**，两处都得解。
- `--limit` 是码率上限触发降 FPS，**不是速度开关**。

### 分段拼接会坏容器（决定性否证）
两段相邻 5s `-f concat -safe 0 -c copy`：
- **roq：250 帧 → 只剩 5.05s，990KB → 222KB，第二段整段丢失**（RoQ 单文件头被复用）
- rm：时长 5.015 → 10.031（漂移 +0.031），容器被重写
- avi / mp4 / flv / asf / mpeg：帧数守恒，时长误差 <0.03s ✅
- 且 `pool.TryTakeLatest`(660) 与滞回 0.18/0.30/0.75/0.80(623-635) 都吃墙钟
  → 提速必然改变 fresh/repeat 比例和自适应阶梯转移点。

### 已实现（用户拍板：turbo 默认关闭 + 并行只给白名单）
1. `--turbo`：解掉输出循环与采集线程两处墙钟节流，改为
   `pool.WaitForFrame()` 数据驱动（否则全变 repeat，产物直接崩）；
   滞回时钟改 **媒体时间** `slots/o.Fps`。实测 20s：21.42s → **1.62s（13×）**。
2. `--parallel N`：`Encoding/ParallelEncoder.cs`，按**整数 slot** 分配段边界
   （不是按秒，否则段内 slot 数凑不齐），并发编码后 concat，带时长校验兜底。
   `Constants.ConcatSafeFormats = [avi,mp4,flv,asf,mpeg]` + `MinShardSeconds=4`，
   roq/rm/过短自动回退并打印原因。三道防线实测生效。

### 又挖出的真瓶颈：固定开销 ~1.5s
turbo 后 20s 与 1s 只差 0.1s。拆解：.NET 启动 0.34s + 能力探测 ~0.9s
+ ffprobe ~0.25s + preflight ~0.2s。已优化：
- **3 次 ffprobe 合并为 1 次** → `Probe.Source()`（`-show_streams -show_format -of json`，
  流时长优先/容器时长兜底，优先级与原来一致）
- Preflight.Video/Audio 并发（fail-fast 语义不变）
- DetectLegacyEncoders/DetectAudioEncoders 并发

### 边际成本表（20s，turbo）——并行净亏损的证据
mpeg1video 0.062 / mjpeg 0.118 / rv20 0.123 / mpeg4 0.164 / wmv2 0.179 /
libx264 0.259 / flv 0.263 / **roqvideo 8.325**。
白名单内边际成本 0.06–0.26s << 每段 1.5s 启动开销 → 20s 源 `--parallel 4`
= 2.33s，比单段 turbo 1.85s 还慢。唯一值得分段的 roqvideo 恰好不能拼接。

### 回归
`compare_matrix.py` **12/12 PASS**、`error_paths.py` **11/11 PASS**（JIT）。

## v7.3：全编码器扫描 + 6 项改进

### 全编码器扫描（32 个 legacy 编码器逐个实测，3s 片段 + turbo）
只有 **AMV 失败**（exit 127，0 字节），其余 31 个通过。

### AMV 根因（4 条硬约束，v6.3.3 全错，属有意偏离基线）
1. AMV 容器**必须有且仅有 2 条流** → 纯视频写完才报 "AMV files only support 2 streams"
2. 音频采样率必须是视频帧率整数倍，合法帧率 10/14/15/18/21/25/30
   （默认 13fps 会被拒："Audio sample rate not a multiple of the frame size"）
3. ADPCM 块大小必须 = 22050/fps（`-block_size:a`，默认 1024 会被拒）
4. 宽高应为 16 的倍数（FFmpeg 只警告，产物播放器打不开）

修复：Constants 加 AmvAudioSampleRate/AmvDimensionMultiple/FormatsRequiringAudio；
EncoderMath 加 AmvAudioBlockSize() + AmvDimensions()，ChooseBaseFps 对 amv 强制
用 AmvFps（原来只在 rates 为空才用）；BuildEncoderCommand 加 `-block_size:a`、
adpcm 不再输出 `-b:a`、无音轨提前报错。
**Preflight.Video 也必须带音轨**（原来 `-an` 纯视频试编码，AMV 必挂）→ 新增
`AudioTrial` 记录 + `audio` 可选参数。

### 另一个 AOT 专属 bug（重要教训）
`System.Text.Json` 反射式序列化在 NativeAOT 下抛
`JsonSerializerIsReflectionDisabled` —— **JIT 版完全正常，只有 AOT 崩**。
配置持久化一加上，AOT 构建启动即崩。
解法：源生成上下文 `[JsonSerializable(typeof(UserConfig))] partial class
UserConfigJsonContext : JsonSerializerContext` + `TypeInfoResolver`，
缩进/null 忽略用 `[JsonSourceGenerationOptions]` 声明。
**教训：新增任何反射型 API 后，必须三套产物都跑一遍，不能只验 JIT。**

### 另一个坑：CJK 对齐
`string.Format("{0,-17}")` 按字符数补空格，而中文在终端里占两列 →
"FFmpeg           :" 和 "可执行文件            :" 冒号对不齐。
解法：`L.DisplayWidth()`（CJK 记 2 列）+ `L.Pad(text, width)`，所有 label 行统一走它。
同理，字符串表里**不要把 `标签 + 空格 + :` 烤进值里**（app.impairments、
report.roqaudio 原来就是这样），要拆成 label / value 两个键。
- **a64 / a64multi5**：FFmpeg 只有 muxer 没有 demuxer，ffprobe 必然报
  "Invalid data found" → 归为 NOPROBE，不是 bug。
- **amv / h263 / roq / h261**：容器不写时长，ffprobe 报 0。
  用纯 ffmpeg 生成的对照文件同样没有时长 → 容器固有行为。
  判断要按**扩展名**而不是 format_name（amv 会被 ffprobe 认成 avi）。
