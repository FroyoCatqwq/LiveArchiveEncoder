# 并行分段编码 —— 猜想验证报告

日期：2026-10-17
被测：`publish/jit/LiveArchiveEncoder.exe`（JIT 构建）
素材：`tests/media/test_src.mp4`（h264/aac，320x240，25fps，20.0s）

---

## 1. 猜想

> 把 00:00-05:00 切成 10 段并行编码再拼接，速度会不会增长？

## 2. 结论（先给答案）

**会增长，但你的猜想找错了瓶颈。**

- 提速幅度确实是 ~N 倍，**前提是拿掉实时节奏**；
- 一旦拿掉实时节奏，**根本不需要并行**——单进程就能快 **58 倍**；
- 并行分段额外引入的代价是：**RoQ 产物损坏、RM 时长漂移、输出内容改变**，
  换来的只是在 58 倍之上再叠几倍。**投入产出比为负。**

---

## 3. 证据 1：墙钟时间 100% 来自主动 sleep，不是 CPU

主循环（`Encoding/RealtimeEncoder.cs`）：

```csharp
552:  double slotInterval = 1.0 / o.Fps;
598:  nextSlot += slotIntervalTicks;
600:  if (nextSlot > nowSlotTicks) HighResolutionTimer.WaitUntil(nextSlot);
```

`--limit` 只是码率上限（触发降 FPS），**不是速度开关**。

实测（rv20 / 25fps / 10s 片段 / `--limit 99999`）：

| 场景 | 墙钟 | 宿主进程 CPU |
|---|---|---|
| 1 路 10s 编码 | **11.54 s** | user 0.108 + sys 0.343 = **0.45 s** |
| **4 路 10s 并行** | **12.15 s** | user 0.232 + sys 0.731 = **0.96 s** |

4 倍工作量，墙钟几乎不变（+0.6s），CPU 只翻倍到 0.96s。
**机器有 4 倍以上余量在空转。**

## 4. 证据 2：真实计算量只占墙钟的 1.4%

用项目实际的滤镜链和编码器单独量 CPU（`ffmpeg -benchmark`）：

| 环节 | 20s 素材 | CPU |
|---|---|---|
| 解码 + `fps=13` + `scale=256:192:flags=neighbor` + `format=yuv420p` | 260 帧 | utime 0.109 + stime 0.141 |
| 编码 rv20 256x192 | 260 帧 | utime 0.016 + stime 0.016 |

**合计 ≈ 0.28 s CPU，对应 20 s 墙钟 → 只用了 1.4% 的算力。**

## 5. 证据 3：去掉节流后上限（决定性）

模拟"无节流直通管道"（解码 → rawvideo pipe → rv20 编码）：

```
real    0m0.345s
产物:   260 帧, duration = 20.000000
```

**20 秒素材 → 0.345 秒，58 倍。产物帧数与时长完全正确。**

对比并行分段：10 段并行理论 10 倍，且要承担下面的风险。

## 6. 证据 4：分段拼接在 legacy 容器上会坏

两段相邻 5s 片段（0-5 / 5-10），`ffmpeg -f concat -safe 0 -c copy` 拼接：

| 编码器 | 容器 | 帧数 s1+s2 → 拼接后 | 时长 | 尺寸 sum → 拼接后 | 判定 |
|---|---|---|---|---|---|
| **roqvideo** | **.roq** | 125+125=250 → **只剩 5.05s** | 应为 10s | 990822 → **222796** | ❌ **数据丢失，彻底损坏** |
| rv20 | .rm | 250 → 探测不到 | 5.015 → **10.031** | 679615 → 681482 | ⚠️ 时长漂移 +0.031，尺寸变了 |
| mpeg1video | .mpg | 250 | 9.98 | 765952 → 765952 | ✅ 字节级一致 |
| wmv2 | .wmv | 250 → 250 | 10.184 | — | ✅ |
| mpeg4 | .avi | 250 → 250 | 10.083 | — | ✅ |
| mjpeg | .avi | 250 → 250 | 10.083 | — | ✅ |
| flv | .flv | 250 → 250 | 10.061 | — | ✅ |
| libx264 | .mp4 | 250 → 250 | 10.023 | 275792 → 274517 | ✅ |

**RoQ 直接废掉**——而 RoQ 正是本项目的核心目标格式之一。RoQ 文件只有一个
文件头，concat 复用第一段头，第二段内容被丢弃。

## 7. 证据 5：输出内容本身依赖墙钟，提速必然改变产物

`RealtimeEncoder.cs` 两处硬依赖墙钟：

```csharp
612:  double now = HighResolutionTimer.MonotonicSeconds();   // 墙钟
623:  double hold = videoRate >= o.LimitKbps * 1.25 ? 0.18 : 0.30;   // 墙钟滞回
626:  if (now - highSince.Value >= hold) currentLevel++;

654:  cadence += effectiveFps / o.Fps;
655:  bool emitFresh = previousIndex < 0 || cadence >= 1.0;
660:  if (pool.TryTakeLatest(out int latestIndex, out long latestSequence))
```

- `TryTakeLatest` 取的是**此刻**采集线程已产出的最新帧 → fresh/repeat 比例是竞态结果；
- 自适应 FPS 的 0.18 / 0.30 / 0.75 / 0.80 秒滞回用的是**墙钟**。

跑得快 → 采集线程来不及供新帧 → repeat 变多；滞回窗口内跨越的帧数变了 →
`currentLevel` 转移点不同。**产物必然改变**，且分段还会让每段重置 `cadence`
与 `currentLevel`，在段边界产生额外伪影。

---

## 8. 判定

| 方案 | 提速 | 是否改变产物 | 风险 | 结论 |
|---|---|---|---|---|
| 并行分段（原猜想） | ~N× | 是 | RoQ 损坏 / RM 漂移 / 段边界伪影 / A-V 漂移 | ❌ 不做 |
| **去掉实时节奏（turbo）** | **~58×** | 轻微（fresh/repeat 比例） | 低，单进程无拼接 | ✅ **做** |
| turbo + 并行叠加 | 58× 之上再几倍 | 是 | 同上全部风险 | ❌ 收益不足以覆盖风险 |

**唯一正确且高效的提速手段是拿掉 `WaitUntil(nextSlot)`，不是并行。**

## 8b. 实测结果：实现之后又发现了一个更靠前的瓶颈

按第 9 节的方案实现 turbo 后重新测量（mpeg4，20s 源，fps 25）：

| 模式 | 墙钟 | 相对实时 |
|---|---|---|
| 实时（默认） | **21.42 s** | 1× |
| turbo | **1.62 s** | **13×** |

但把时长从 20s 缩到 1s，墙钟几乎不变（1.50s vs 1.62s）——
**说明 turbo 之后剩下的时间全是固定开销，不是编码。** 逐项拆解：

| 阶段 | 耗时 |
|---|---|
| .NET 进程启动（`--help`，零子进程） | 0.34 s |
| FFmpeg 能力探测（`-encoders` ×2、`-filters`、`-h filter=scale`、`-h encoder=X`） | ~0.9 s |
| ffprobe 探测（改动前 3 次：Stream / Duration / HasAudio） | ~0.64 s |
| Preflight（Video + Audio，各一次短编码） | ~0.32 s |

**约 1.5 s 固定开销，其中 ~1.15 s 是 10 余次彼此独立的子进程启动。**

### 固定开销 vs 边际成本（20s 源，turbo）

| 编码器 | 1s（≈固定） | 20s | 边际 |
|---|---|---|---|
| mpeg1video | 1.790 | 1.852 | **0.062** |
| mjpeg | 1.810 | 1.928 | **0.118** |
| rv20 | 1.712 | 1.835 | **0.123** |
| mpeg4 | 1.681 | 1.845 | **0.164** |
| wmv2 | 1.703 | 1.882 | **0.179** |
| libx264 | 1.790 | 2.049 | **0.259** |
| flv | 1.735 | 1.998 | **0.263** |
| **roqvideo** | 2.210 | 10.535 | **8.325** |

这张表把并行的价值彻底否掉了：

- 白名单内所有编码器的边际成本只有 **0.06–0.26 s**，
  而每段要额外付 **~1.5 s** 启动开销 → **分段必然净亏损**；
- 唯一边际成本够高、值得分段的编码器是 **roqvideo（8.3s）**，
  而 roq 恰恰是拼接会丢数据的那个容器，不在白名单里。

实测印证：20s 源 `--parallel 4` = **2.33 s**，比单段 turbo 的 **1.85 s 还慢**。

### 已做的固定开销优化

1. **3 次 ffprobe 合并为 1 次** —— 新增 `Probe.Source()`，
   一次 `-show_streams -show_format -of json` 同时拿到视频流元数据、
   时长（流时长优先、容器时长兜底，与原来的优先级一致）和音轨是否存在；
2. **Preflight.Video / Preflight.Audio 并发** —— 两者只是独立的"提前失败"探测，
   任一方抛错仍在写出任何输出之前中止，fail-fast 语义不变；
3. **DetectLegacyEncoders / DetectAudioEncoders 并发** —— 两次独立的 `ffmpeg -encoders`。

剩余可做的（未实现）：能力探测结果按 ffmpeg 路径 + 版本缓存到磁盘；
以及用 NativeAOT 发布把 0.34 s 的 .NET 启动压到 ~0.05 s。

## 9. 建议的实现方向（待确认后动手）

1. 新增 `--turbo`（或 `--no-realtime`）开关，**默认关闭**，保持现有语义；
2. turbo 模式下把墙钟 deadline 换成**采集线程驱动**——等"有新帧"而不是等墙钟，
   否则 `TryTakeLatest` 会因采集跟不上而全变成 repeat，产物直接崩坏；
3. turbo 模式下把自适应滞回的 0.18/0.30/0.75/0.80 从**墙钟秒**换成**媒体时间秒**，
   否则窗口内跨越的帧数会暴涨，`currentLevel` 行为失真；
4. 保留 `--limit` 的码率控制逻辑不变（它按媒体时间统计，天然与速度无关）；
5. 不做拼接，不引入多进程。
