# v8 多语言（i18n）

> 状态：**机制已落地，一个命令完整翻译**（2026-10-31）
> 库：[`I18Next.Net`](https://github.com/DarkLiKally/I18Next.Net) 2.0.0（Apache-2.0）

## 1. 为什么用 i18next 而不是手写字典

这个项目的字符串有三个特点，手写字典会在第二个月开始疼：

- **键是嵌套的**（`history.total`），不是平的；
- **句子里有占位符**（"共 {{runs}} 次运行，记录在 {{path}}"），而中英文里数字的位置不一样；
- **英文要复数，中文不要**。今天用 `run(s)` 糊过去，明天就会有人写出 `"{0} run(s)"`，
  后天第三条路径又是另一种写法。

这三个都是 i18next 存在的理由。它还是 JS 版 i18next 的移植，翻译文件格式和 Web 端通用——
如果将来有个网页版界面，资源可以直接共用。

## 2. 分层

| 位置 | 东西 | 为什么在这 |
| --- | --- | --- |
| `Lae.Core/Localization/IMessages.cs` | `IMessages`、`KeyMessages`、`LanguageChoice` | 纯逻辑：接口和"选哪个语言"的规则，零 I/O，可单测 |
| `Lae.Media/Localization/I18NextMessages.cs` | i18next 实现、内嵌资源读取 | 读资源是 I/O，和 `TomlSettingsStore` 同理 |
| `Lae.Media/Localization/locales/{en,zh}/translation.json` | 翻译文件 | 内嵌进程序集 |

**资源内嵌，不放二进制旁边。** v8 是自包含单文件发布，一个散落的 `locales/` 目录会是用户下载包里
第一个丢的东西。csproj 里用 `LogicalName` 把资源名钉死成 `lae.locales.{语言}.{命名空间}.json`，
查找不依赖 MSBuild 的目录转点号规则。

## 3. 语言怎么选

```
LAE_LANG  →  ui.language（settings.toml）  →  en
```

- **规范化**：`zh-CN`、`zh_CN`、`ZH`、`zh-Hans` 都归到 `zh`。
- **不认识的语言落到 en**，不是报错：配置里手写一个 `fr` 不该让程序不会说话。
- **环境变量优先**，这是让 e2e 能测语言切换的唯一干净办法——否则测试要往开发者的
  `%LOCALAPPDATA%` 写设置文件，那正是 v7 e2e 栽过的坑。

```toml
# settings.toml
[ui]
language = "zh"
```

```powershell
$env:LAE_LANG = "zh"; lae history list
```

## 4. 翻译的规矩

1. **一条句子一个键，不拼**。`"{0} runs"` + `"at " + path` 这种写法在中文里语序就错了。
2. **占位符用 `{{name}}`**，值通过匿名对象传：`messages.Get("history.total", new { runs, path })`。
3. **别把变量叫 `count`**。i18next 里 `count` 会触发复数解析，而默认复数解析器读的是
   JSON v1 格式的 `key_plural` 后缀，配错了就是拿到键名。本项目暂时不用复数，
   所以叫 `runs` 而不是 `count`。
4. **缺翻译返回键名，不抛异常**。缺一条翻译是资源文件的缺口，不能让命令失败。

## 5. 进度

**已完整翻译**：`lae history`（`history.header` / `empty` / `total` / `limit`）。

**还没翻译**（约 90 条，按文件）：

| 文件 | 大致条数 | 内容 |
| --- | --- | --- |
| `Lae.App/EncodeSession*.cs` | ~35 | 编码报告、错误、note |
| `Lae.App/Commands/ConfigCommand.cs` | ~15 | 键值标签、迁移说明 |
| `Lae.App/Commands/PresetCommand.cs` | ~15 | 预设列表、增删结果 |
| `Lae.App/Commands/SetupCommand.cs` | ~8 | 工具链诊断 |
| `Lae.App/Commands/EncodeCommand.cs` | ~10 | 选项的 `Description`（进 `--help`） |
| `Lae.Core/Encoding/*` | ~20 | 计划问题（`EncodePlan.Problems`、字幕、二次压缩） |

**为什么先只做一个命令**：把 90 条一次性搬完，出问题时无法判断是机制错了还是某条键写错了；
一个命令端到端跑通（含 e2e 三条入口），剩下的就是机械替换。Core 里的那 20 条要多一步设计——
它们是纯逻辑层产生的句子，得把 `IMessages` 传进 `EncodePlan.Create` 这类函数，属于下一轮的第一件事。

## 6. 加一条新字符串

1. 在 `locales/en/translation.json` 里按层级加键；
2. 在 `locales/zh/translation.json` 里加同名的中文；
3. 代码里 `messages["a.b.c"]` 或 `messages.Get("a.b.c", new { x })`；
4. 命令的构造函数已经能拿到 `IMessages`（`CommandTree` 传的 `host.Messages`），不需要新建。

## 8. 已知限制

- **表头与 CJK 对齐**：`history list` 的中文表头按字符数排，不按显示宽度（中文占两格），
  所以和 ASCII 数据列略有错位。要做对得引入东亚宽度计算，暂时不值得。
  数据列本身不受影响。
- **`--help` 的选项说明还是英文**：`Option.Description` 在命令构建时就固定了，
  翻译它需要把 `IMessages` 提到命令树构建之前——和"命令自己加载设置"是同一个改造，一起做。
- **没有 `LAE_LANG=zh` 的补全脚本**：补全候选来自命令树，与语言无关，不需要。
